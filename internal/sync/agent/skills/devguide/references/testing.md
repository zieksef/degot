# 测试规范

## 测试组织

测试按长期稳定的行为组织，不按修改次数或实现历史组织。

新增或修改测试前，必须先检查现有测试。回归场景能够由现有测试函数或表驱动用例表达时，必须扩展或调整现有用例，不得仅因本次修改而新增测试函数。

只有新增独立行为边界、需要不同测试准备，或合并后会导致测试职责混乱时，才新增测试函数。不得为了减少测试函数数量，把互不相关的行为塞进同一个测试。

## 回归测试

修复缺陷时，测试必须描述长期稳定的预期行为，并能在修复前失败、修复后通过；不得以本次缺陷、工单或修改内容命名长期保留的测试。

行为发生变化时，必须更新或替换过时断言，并删除重复、过时或不再表达有效行为的测试。

## 何时修改测试

不要求每次代码修改都新增或修改测试。

- 现有测试已经覆盖目标行为时，只运行现有测试验证，不新增测试。
- 新增可观察行为或修复此前未覆盖的缺陷时，优先调整最接近的现有测试或增加用例。
- 纯重构或内部实现替换且外部行为不变时，不为本次修改机械增加测试。
- 用户明确要求不补测试时，不新增测试；运行现有可行测试完成验证。
